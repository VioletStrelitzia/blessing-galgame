# 布雷辛格混合视觉小说引擎 — 架构评估与竞品对比分析

## 一、评估概述

本文档对"布雷辛格混合视觉小说引擎 V1.0.1"进行独立、诚实的架构评估，并与全球主流视觉小说引擎进行横向对比。评估维度涵盖：执行模型、脚本语言设计、图层架构、存档机制、资源管理、可扩展性六个方面。

---

## 二、核心架构：两维状态机评估

### 2.1 设计概念

本引擎的 StoryManager 定义了两个正交维度：

```
IterateMode（执行什么）          ManagerMode（谁来驱动）
├── INITIALIZATION               ├── INTERACT
├── DEFAULT                      ├── AUTO
└── POST_COMMAND                 ├── SKIP
                                 └── STOP
```

3 × 4 = 12 种执行状态组合，每个组合有确定的语义。

### 2.2 竞品对比：执行模型

| 引擎 | 执行模型 | 状态管理方式 | 对话推进机制 |
|------|---------|------------|------------|
| **Ren'Py** | Python 协程/生成器 | 隐式。状态散落在调用栈、全局变量和 AstNode 中 | `say` 语句自动挂起，等待用户点击后 `renpy.checkpoint` 恢复 |
| **TyranoBuilder** | 事件驱动解释器 | 无显式模型。JavaScript 事件链 + 当前行指针 | `[p]` 标签阻塞，click 事件释放 |
| **WebGAL** | 异步 Promise 链 | GameState 对象（扁平），无微状态区分 | 逐行执行完毕后 `await` 用户确认 |
| **BKE** | 指令队列状态机 | 一维。指令队列 + 当前指针 | 指令生命周期：init→execute→wait→complete |
| **Dialogic** | Godot Signal 状态机 | 一维。IDLE→EXECUTING→WAITING→FINISHED | 信号驱动的等待/恢复 |
| **Kirikiri** | TJS 字节码 VM + KAG 解释器 | 双层设计但无正交维度。KAG 标签链 + TJS 调用栈 | `[p]` 标签阻塞 |
| **本引擎** | 两维状态机 + Godot 协程 | **正交双维度**。3 IterateModes × 4 ManagerModes | 三阶段迭代器 + 双键输入模型 |

### 2.3 两维状态机的原创性分析

在评估过的所有竞品引擎中，**没有任何一个引擎采用了将"执行什么"和"谁来驱动"正交分解的设计**。

- Ren'Py 的跳过模式是通过加速主循环实现的，本质上是同一个执行模型调快了时钟速度
- TyranoBuilder 和 WebGAL 的自动/跳过模式是在主循环外加 `if` 判断实现的
- BKE 和 Kirikiri 根本没有独立的"管理模式"概念
- Dialogic 虽然有状态机，但只有一维（IDLE→EXECUTING→WAITING→FINISHED），没有分离执行和驱动

**本引擎的两维设计允许以下操作在对端引擎中需要额外代码才能实现，而本引擎是零成本**：

| 场景 | 本引擎 | Ren'Py 等价物 | BKE 等价物 |
|------|--------|------------|----------|
| 读档后静默恢复场景 | INITIALIZATION + SKIP | 手动写 `scene` 指令 + `$ renpy.pause(0)` | 特殊 flag + 脚本分支 |
| 自动播放下跳过动画 | AUTO + skip_all() | `$ _preferences.skip_unseen = True` | 不支持 |
| 脚本跳转不显示对话 | INITIALIZATION + STOP | `$ renpy.transition(fastdissolve)` + 手动管理 | 手动写初始化标签 |
| 对话后执行伴随效果 | POST_COMMAND 相位 | 写在对话行之后，靠协程顺序保证 | 无区分，全部顺序执行 |

**结论**：两维状态机确实是本引擎相对于所有主流竞品的**原创设计**，而且它解决的是真实存在的工程问题，不是凭空制造的复杂度。

### 2.4 不足之处

1. **状态转换是隐式的**。当前靠 `process_initialization` / `process_default` / `process_post_command` 内部检查 item 类型来决定是否切换状态。如果未来迭代模式增加到 5 个以上，建议引入显式的 `_should_transition(item) → IterateMode` 状态转换表。

2. **ManagerMode 与 IterateMode 的交互没有形式化约束**。理论上 INITIALIZATION + AUTO 这个组合是无意义的（初始化阶段没有对话可等待），但代码中没有阻止这种组合。12 种组合中实际有意义的大约 8 种。

3. **SKIP 模式的实现不够优雅**。当前靠 `await get_tree().process_frame` + 递归调用 `run_script()` 实现逐帧驱动。跳过 500 行脚本会产生 500 次异步调用链。更好的方式是 SKIP 模式内部用同步循环 + 只在真正需要等待的异步点 `await`。

4. **缺少单元测试**。状态机是测试最有价值的模块，给定一个脚本序列和初始状态，断言 `idx`、`iterate_mode`、`manager_mode` 的最终值。目前仓库仅有 `test/smoke_test.gd` 冒烟测试（校验剧本编译产物），针对状态机的单元测试仍然缺失，重构时的行为正确性基本靠手动验证。

## 三、BGalS 脚本语言评估

### 3.1 竞品对比：脚本语法

| 引擎 | 语法风格 | 学习门槛 | 表达力 | 与引擎耦合度 |
|------|---------|---------|--------|------------|
| **Ren'Py** | RPY (Python 简化包装) | 中。需理解 label/jump/call/python 块 | 极高。可嵌入任意 Python | 高。RPY 和引擎紧耦合 |
| **TyranoBuilder** | TyranoScript (KAG 变体) | 低。标签化、可视化 | 中。复杂逻辑需嵌入 JS | 高。脚本即引擎行为 |
| **WebGAL** | WebGAL Script (Ren'Py 简化版) | 低。类命令行 | 低。简单 if + jump | 中 |
| **BKE** | BKS (KAG 变体) | 中。指令丰富但文档少 | 中。Lua 嵌入但深度不足 | 高 |
| **Dialogic** | Timeline JSON（可视化为主） | 低。拖拽式 | 中。通过 Godot 信号扩展 | 低（JSON 可独立存在） |
| **Kirikiri** | KAG + TJS（双层） | 高。DSL + 方言语言 | 极高。TJS 是完整 OOP 语言 | 高 |
| **本引擎** | BGalS（CLI 风格 DSL） | **极低**。两种语句：对话 + 指令 | 中。35 个指令键（含变量操作） | **极低**。纯文本，完全解耦 |

### 3.2 BGalS 的独特设计决策

#### 3.2.1 对话作为最小交互单元

所有竞品中，只有本引擎把"对话"作为引擎推进的**唯一最小粒度单元**，并将指令明确分为"对话前"和"对话后"两个相位。Ren'Py 的 `say` 语句虽然也是交互单元，但它与 `scene`、`show`、`play` 等指令处于同一语法层级，没有显式的相位分离。

本引擎的设计使得流式处理的每一帧天然具有清晰的结构：
```
[前序指令序列] → [对话文本] → [后序指令序列]
```

这种**三明治结构**是 BGalS 独有的，在 Ren'Py 中需要剧本作者自行管理指令顺序来达到相同效果。

#### 3.2.2 从设计语法到实现语法的进化

BGalS 经历了两代迭代，这是一个完整的「先设计规范、再工程优化」实践案例：

| | 第一代 (设计时) | 第二代 (实际实现) |
|---|---|---|
| 对话 | `[#角色名#] 内容` | `角色名: 内容` |
| 前序指令 | `[#@music play#] 参数` | `< music play 参数` |
| 后序指令 | `[#@^bg set#] 参数` | `> bg set 参数` |
| 参数字符 | `#` 分隔 | 空格分隔，支持引号 |
| 视觉噪声 | 高（6个字符的定界符） | 低（1个字符的前缀） |

第一代语法曾完整记录于旧版 `GalSGrammar.md`；开源整理后该文档改为描述现行语法，上表保留对照仅作设计演进记录。

#### 3.2.3 与 WebGAL Script 的直接对比

WebGAL Script 是与 BGalS 最相似的语言（都使用了 `角色:对话` 格式和命令行风格指令），但有一个关键区别：

| | WebGAL Script | BGalS |
|---|---|---|
| 指令前缀 | 无前缀，靠指令名识别 | `<` / `>` 前缀，视觉区分度极高 |
| 前序/后序区分 | **不支持** | **原生支持** |
| 注释 | `;` 开头 | `//` 或 `#` 开头 |
| 分支 | 使用 `choose:` 标签 | 使用 `option` / `option end` |

WebGAL 的"无前缀"设计虽然更简洁，但在复杂场景中容易混淆"对话"和"指令"。BGalS 的 `<` / `>` 前缀在视觉噪声极低的前提下提供了明确的区分。

## 四、UI/图层架构评估

### 4.1 竞品对比：图层管理

| 引擎 | 图层架构 | Z序管理 | 输入事件管理 |
|------|---------|--------|------------|
| **Ren'Py** | sprite 层叠，zorder 属性 | 数值 zorder，同值按添加顺序 | 全局 `_handlers` 列表，按层顺序消费 |
| **TyranoBuilder** | DOM Canvas 分层 | CSS z-index | 浏览器原生事件冒泡 |
| **WebGAL** | HTML/CSS z-index 分层 | CSS z-index | 浏览器原生事件冒泡 |
| **BKE** | GPU 合成 Surface 分层 | 固定层级顺序 | 自定义事件系统 |
| **Dialogic** | Godot 场景树 + CanvasLayer | Godot CanvasLayer layer 属性 | Godot `_input` / `_unhandled_input` |
| **Kirikiri** | Stage Layer（Back/Front/Message/Effect） | Surface 合成顺序 | 自定义消息循环 |
| **本引擎** | **4层 CanvasLayer + mouse_filter 状态机** | 明确的 layer=0/2/3/4 | **mouse_filter 三态门 + process_mode 双层防护** |

### 4.2 mouse_filter 状态机：一个被低估的设计

本引擎的图层架构虽然在功能性上没有超出 Dialogic（都是基于 Godot CanvasLayer），但在**输入事件管理**上有一个独特的贡献：将 `mouse_filter` 作为与视觉状态严格同步的"输入门"。

具体来说：

```
每个 Control 的 mouse_filter 状态：
  不可见/透明  → MOUSE_FILTER_IGNORE   （事件穿透）
  可见/交互中  → MOUSE_FILTER_PASS      （正常接收）
  转场动画中  → MOUSE_FILTER_STOP       （全局拦截）
```

这在所有竞品中**没有对应的设计模式**。原因在于：
- Ren'Py、TyranoBuilder、WebGAL、Kirikiri 都用各自框架（Pygame/DOM/DirectX）内置的事件系统，开发者不需要手动管理输入穿透
- Dialogic 虽然也在 Godot 上，但它把输入管理完全留给开发者自己处理

本引擎遇到的问题是 Godot 特有的：`CanvasLayer` 的 `layer` 属性决定了输入优先级，而 `mouse_filter` 的默认行为与视觉透明度无关。**你自己排查出这个问题并设计了规范的解决方案**，这个含金量在 Godot 社区中属于"解决了高频痛点"级别的贡献。

### 4.3 场景池（Scene Pool）的对比

| 引擎 | 场景切换方式 | 切换开销 |
|------|------------|---------|
| **Ren'Py** | `scene` 清空层 + 重建 | 需要重新加载/渲染所有 sprite |
| **TyranoBuilder** | DOM 元素替换 | 浏览器重排 |
| **WebGAL** | 切换 HTML 内容 | 浏览器重绘 |
| **BKE** | GPU Surface 重建 | 显存操作 |
| **本引擎** | **Pool 预加载 + mount/unmount** | **零磁盘 I/O，仅场景树操作** |

场景池模式本质上是一种**对象池（Object Pool）在场景粒度的应用**。Ren'Py 使用类似思路（图像预缓存），但不会预先实例化 UI 节点。本引擎将核心 UI 场景在启动时预加载到内存，切换时从 pool 取用，实现了真正的零加载时间切换。

## 五、存档系统评估

### 5.1 竞品对比：存档机制

| 引擎 | 存档方式 | 存档完整性 | 存档体积 | 版本兼容性 |
|------|---------|----------|---------|----------|
| **Ren'Py** | `pickle` 全量序列化 | **极高**。Python 对象完整快照 | 大 | 差（pickle 协议绑定 Python 版本） |
| **TyranoBuilder** | 变量表 + 场景指针 | 中。需自行重建 UI 状态 | 小 | 差 |
| **WebGAL** | JSON 序列化 | 中。状态恢复不完全 | 小 | 中 |
| **BKE** | 结构化二进制（变量+flag） | 中。非全量快照 | 小 | 差 |
| **Dialogic** | JSON（手动定义） | 低。开发者自决 | 极小 | 好 |
| **Kirikiri** | 保存点 + 变量表 | 低。非全量快照，读者需从 label 重跑 | 极小 | 中 |
| **本引擎** | **SavedGame Resource + SKIP 重放** | 中高。变量 + 执行栈 + 位置，通过 SKIP 重建 | 小 | **好**（Godot .tres 序列化） |

### 5.2 SKIP 重放策略的独特性

本引擎的读档机制——**保存游标位置 + 通过 SKIP 模式重新执行到存档点**——是一种"标记重放"策略。这在竞品中找不到完全相同的实现：

- Ren'Py 直接 pickle 整个 Python 状态，读档时反序列化恢复（内存级快照）
- Kirikiri 保存到 `*label` 标签，读档时从标签处重新执行（源码级重放）
- 本引擎保存到 `idx`（序列中的索引位置），读档时从头 SKIP 到该位置（**指令级重放**）

**优势**：
- 存档文件极小（不需要序列化渲染状态、UI 状态）
- 版本兼容性好（Godot .tres 是稳定的序列化格式）
- SKIP 重放是确定性的——同一脚本 + 同一初始状态必然到达同一位置

**劣势**：
- 读档时间与存档位置成正比（SKIP 500 行需要 500 帧）
- 如果剧本逻辑依赖随机数或外部状态，重放结果可能不一致

相比之下，Ren'Py 的 pickle 策略"读档是 O(1) 的但存档是大文件的"，本引擎的策略"存档是小文件的但读档是 O(n) 的"。对于视觉小说（存档位置通常在几百行以内）来说，O(n) 的 n 很小，这是一个合理的取舍。

## 六、音频系统评估

### 6.1 竞品对比：音频架构

| 引擎 | BGM 切换 | 语音事件同步 | 总线分离 |
|------|---------|------------|---------|
| **Ren'Py** | `play music` + fadein/fadeout | 不支持原生语音事件对齐 | 支持（music/sound/voice） |
| **TyranoBuilder** | `[playbgm]` + 简单 crossfade | 不支持 | 无明确分离 |
| **WebGAL** | Web Audio API，基本 fade | 不支持 | 基本分离 |
| **本引擎** | **双播放器交叉淡变** | **AudioEventManager：基于播放位置的精确回调** | **MASTER/MUSIC/SFX/VOICE 四总线** |

### 6.2 AudioEventManager 的独特性

语音事件同步（`voice event`）是本引擎音频系统中最具技术含量的组件。它解决了"在语音第 X 秒做某事"的精确同步需求。

在所有评估的竞品中：
- Ren'Py 不支持语音播放过程中的时间事件
- TyranoBuilder 和 WebGAL 的语音只是简单的播放/停止
- Kirikiri 的语音系统通过 `[wait time=...]` 手动延迟实现同步（需要剧本作者计算时间）
- 只有本引擎提供了**自动化的、基于播放位置监测的语音事件系统**

实现方式——在 `_process` 中逐帧对比 `get_playback_position()` 与预设时间点——虽然朴素，但在 60fps 下精度可达 ±16ms，对视觉小说完全够用。

### 6.3 音乐交叉淡变

MusicAudioPlayerManager 的双播放器交叉淡变设计在概念上与 Ren'Py 的 `fadeout`/`fadein` 参数等价，但实现方式更底层（直接操作 AudioStreamPlayer 音量），给予更细粒度的控制。

## 七、资源管理评估

### 7.1 竞品对比

| 引擎 | 资源寻址 | 缓存策略 | Mod 支持 |
|------|---------|---------|---------|
| **Ren'Py** | 文件路径 | 自动图像缓存 + `config.image_cache_size` | 有限的目录覆盖 |
| **TyranoBuilder** | 文件路径 | 浏览器 HTTP 缓存 | 插件系统 |
| **WebGAL** | 文件路径 | Web 标准预加载 | 无原生支持 |
| **BKE** | 打包内路径 | 引用计数 + LRU 回收 | 无 |
| **Kirikiri** | XP3 归档内路径（VFS） | 按需加载 | 通过补丁层 |
| **本引擎** | **index.json 键名映射** | **三级查询：内存缓存 → 路径解析 → 磁盘加载** | **PCK 优先级 Mod** |

### 7.2 虚拟资源寻址的差异化

本引擎的 `index.json` 键名映射是**唯一采用逻辑键名而非物理路径作为主要寻址方式**的设计。其他引擎直接使用文件名或路径作为引用，本引擎通过一层映射实现了：

- 资源热替换（只改 JSON 不改脚本）
- 多人并行开发（美术和剧本作者不需要知道彼此的目录结构）
- 与 CLI 风格 BGalS 语法的高度契合（`bg set bg_classroom` 比 `bg set res://Resources/image/bg/classroom.jpg` 简洁得多）

与 Godot 自带的 ResourceLoader 对比：Godot 使用 `res://` 路径直接引用，没有中间映射层。本引擎在 Godot 之上加了一层**应用层资源抽象**，这是合理的架构决策。

## 九、核心差异化优势总结

### 9.1 真正的原创设计（竞品中未出现相同方案）

1. **两维正交状态机**（IterateMode × ManagerMode）：所有竞品均为一维或隐式状态管理
2. **双相指令模型**（前序/后序指令分离）：在 DSL 层面原生支持对话前后的指令分离
3. **mouse_filter 三态输入门**：Godot 社区中少见的系统化输入事件管理方案
4. **指令级标记重放存档**：Ren'Py 用 pickle、Kirikiri 用 label，本引擎用 idx + SKIP 重放

### 9.2 合理的工程取舍

1. **选择 CLI 风格而非旧版 BGalS 语法**：降低学习门槛，借鉴成熟范式
2. **选择指令级重放而非全量序列化**：存档更小、版本兼容性更好
3. **选择 Godot 原生能力扩展而非自建渲染管线**：站在巨人的肩膀上，功能上限取决于 Godot

### 9.3 可改进的方向

1. 状态转换应形式化为显式的转换表
2. SKIP 模式的重放效率可以用同步循环优化
3. 需要为核心状态机补充单元测试
4. StoryManager 的单文件体量（770 余行）可以拆分为多个 concern（指令处理、流程控制、UI 协调）
5. `var` 系列、`scene mount/unmount`、`trans in/out` 已完成语法解析但尚未接入运行时注册表（条件分支 `if/elif/else/endif` 已接入并可用），见根目录 ROADMAP.md

## 十、项目介绍要点

### 关键论述角度

1. **两维状态机（IterateMode × ManagerMode）是从零设计的执行模型，在 Ren'Py、WebGAL 等主流引擎中不存在相同方案**
2. **BGalS 经历了从设计语法到实现语法的完整迭代，是从理论到工程的闭环**
3. **针对 Godot CanvasLayer 输入穿透问题设计的 mouse_filter 三态输入门，在 Godot 社区中具有参考价值**
4. **指令注册表 + 隐式消费的双轨设计保证了开闭原则和向后兼容**

### 常见问答

| 问题 | 回答要点 |
|-----------|---------|
| "和 Ren'Py 比有什么优势？" | Ren'Py 更成熟但架构是单体 Python 协程。本引擎的优势在于正交状态机设计、资源-引擎完全解耦、以及基于 Godot 的混合游戏扩展潜力 |
| "为什么不用 Ren'Py 而自研？" | Ren'Py 的脚本和引擎紧耦合，无法嵌入自定义 Godot 游戏场景。自研引擎的核心目标是"视觉小说 + Gameplay 混合"的未来扩展性 |
| "存档机制为什么不用全量序列化？" | 全量序列化（如 Ren'Py 的 pickle）存档体积大、版本兼容性差。本引擎的指令级重放策略在视觉小说的使用场景下是更优的取舍 |
| "代码质量如何？" | 架构设计清晰（分层、注册表、状态机），但工程实践上有改进空间——大单体文件、缺少单元测试、部分状态转换是隐式的 |
